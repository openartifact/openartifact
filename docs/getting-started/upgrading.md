# Upgrading

Upgrade by replacing the binary or image; the database schema is migrated forward automatically at startup.

Checklist:

1. Read the release notes on the [GitHub releases page](https://github.com/openartifact/openartifact/releases) (generated by GoReleaser from the git history, grouped into Features, Bug fixes, CI and build, Other).
2. Back up the database and blob store ([backup](../operations/backup.md)) and make sure the [secrets](#secrets-to-preserve) are stored safely.
3. Deploy the new version ([Docker Compose](#docker-compose), [Helm](#helm), [binary](#binary)).
4. Check `GET /health`: the JSON `version` field shows the running version and `status` should be `healthy`.

## Versions and image tags

- The `VERSION` file at the repository root is the release version. Releases are cut from tags `vX.Y.Z`; the release workflow fails unless `VERSION` equals the tag without the `v`. A tag containing a `-` (for example `v1.0.0-rc.1`) is a pre-release.
- Images are published to `ghcr.io/openartifact/openartifact` for `linux/amd64` and `linux/arm64` with tags `X.Y.Z` (no `v`) and `X.Y`; `latest` is only moved by tags without a pre-release suffix. Pin an exact `X.Y.Z` in production.
- Release archives (`openartifact_<version>_<os>_<arch>.tar.gz`, `oa_...`) and `SHA256SUMS` are attached to the GitHub release; see [installation](installation.md#release-archives) and [signing](../security/signing.md) to verify them.
- A binary built without `-ldflags` reports version `dev`. The compose file builds from the checkout and takes the version, commit and build time from `OPENARTIFACT_VERSION`, `OPENARTIFACT_COMMIT` and `OPENARTIFACT_BUILD_TIME` (defaults `dev`, `unknown`, `unknown`); `make docker-up` fills them from the `VERSION` file and git. `openartifact-server -version` prints what a binary was stamped with.

## Database migrations

- Migrations are SQL files embedded in the binary (`migrations/`) and applied in file-name order. Applied versions are recorded in the `schema_migrations` table (`version`, `applied_at`, `checksum`, the SHA-256 of the file).
- They run automatically at every start unless `MIGRATE_ON_START=false`, under a PostgreSQL advisory lock, so several replicas can start at once and only one applies each migration. Each file runs in its own transaction; files named `*.no_tx.sql` run without one, one statement at a time (needed for `CREATE INDEX CONCURRENTLY`, which cannot run in a transaction).
- **Forward-only.** There are no down migrations. An applied file must never change: if the checksum of an applied migration differs from the one in the binary, the migrator aborts with a `checksum drift` error instead of continuing.
- A failed migration is rolled back (transactional files) and the server logs `auto-migrate failed` and exits with status 1.
- Running a new binary against an old database applies the pending migrations; there is no dry-run mode.

### Migrating separately from the rollout

Set `MIGRATE_ON_START=false` (the exact lowercase string; other values keep migrations on) and run the migrations as a one-off step before starting the new version, with the same database settings:

```sh
./openartifact -migrate                     # binary: applies migrations and exits
docker compose -f docker/docker-compose.yml run --rm openartifact ./openartifact -migrate
```

With `MIGRATE_ON_START=false` the server logs `automatic migrations skipped` at start and does not check the schema version, so a new binary against an unmigrated database may fail at query time. `make migrate` does the same from a source checkout (`go run ./cmd/server -migrate`).

## Docker Compose

From the checkout of the new version:

```sh
git fetch --tags && git checkout vX.Y.Z
make docker-up    # same as docker compose -f docker/docker-compose.yml --env-file docker/.env up -d --build, plus build metadata
```

This rebuilds the `openartifact` image and recreates the container; the named volumes (`postgres_data`, `artifacts_data`, `backups_data`) are kept. `docker compose down -v` deletes them, do not use it for an upgrade. Migrations run when the new container starts. To run a released image instead, point the service at `ghcr.io/openartifact/openartifact:<version>` and use `docker compose pull && docker compose up -d`. The compose file pins the PostgreSQL major version (`postgres:18-alpine`); it is not changed by an OpenArtifact upgrade.

## Helm

The chart is versioned separately from the application (the chart `version` and `appVersion` differ). The image tag defaults to the chart's `appVersion`; override with `image.tag`.

```sh
helm upgrade openartifact oci://ghcr.io/openartifact/charts/openartifact \
  --namespace openartifact -f my-values.yaml
# classic repository: helm repo update && helm upgrade openartifact openartifact/openartifact -n openartifact -f my-values.yaml
```

- Pods apply migrations at startup (`config.migrateOnStart`, default `true`) under the advisory lock. During a rolling update, old pods keep running against the already-migrated schema until they are replaced; nothing in the project guarantees that an older version works with a newer schema.
- With a single `ReadWriteOnce` volume the Deployment uses `Recreate`, so an upgrade has a short downtime. Object storage or `ReadWriteMany` allows rolling updates.
- The generated Secret (`AUTH_HMAC_KEY`, `OPENARTIFACT_SECRET_KEY`) is reused on upgrade through Helm's `lookup`. That does not work under `helm template`: with Argo CD or similar, create the Secret yourself and set `secrets.existingSecret`. Option reference and details: [chart README](https://github.com/openartifact/helm-charts/blob/main/charts/openartifact/README.md).

## Binary

Stop the old process, replace the `openartifact` binary (and `resetpw`) with the new release, then start it with the same configuration. Run `./openartifact verify openartifact.yaml` first to catch configuration errors; compare your file against the new `openartifact.example.yaml` and root [`.env.example`](../../.env.example) for added keys ([configuration](configuration.md)).

## Secrets to preserve

Keep these identical across upgrades, restores and replicas:

| Setting | If lost or changed |
|---|---|
| `OPENARTIFACT_SECRET_KEY` | Values stored encrypted (`enc:v1:...`: webhook secrets, upstream passwords, SSO client secrets, AI keys, storage credentials) can no longer be decrypted. Removing the key entirely makes reading them fail; setting it for the first time leaves existing plaintext values readable |
| `AUTH_HMAC_KEY` | Signs OIDC/SAML login state. If unset, a random key is generated at every start; logins in flight during a restart, or handled by a different replica, fail. Sessions and API tokens are not affected |
| `OPENARTIFACT_SAML_SP_CERT` / `_KEY` | Without them an ephemeral keypair is generated per process; the IdP registration must be redone after each restart |
| `BASE_URL` | SAML entity ID and ACS URL, and links in generated indexes, are derived from it; changing it breaks existing IdP registrations |

Docker Compose only passes `AUTH_HMAC_KEY` through; see [installation](installation.md#docker-compose) for adding the others. The `docker/.env` file and any compose override belong in your backup.

## Version notes

### Next release: organizations become projects

**Requires a Recreate upgrade.** Stop all old replicas before starting the new version; do not use a rolling upgrade. The migration renames tables the old binaries still query, so old and new replicas cannot run side by side.

Schema:

- Tables `organizations` -> `projects` and `organization_members` -> `project_members`; columns `org_id` -> `project_id` (repositories, members, audit log). New table `project_groups` (group grants on a project) and policy columns on `projects`.
- Audit actions for these objects are now `project.*`.

Role mapping of existing members: `admin` -> `maintainer`, `member` -> the project's old `member_role` (`read` -> `viewer`, `write` -> `developer`, `admin` -> `maintainer`). `owner` is unchanged. Where this raises access (a plain member whose old `member_role` was `admin` becomes `maintainer`, which can also delete) it is safe, because organizations could only be managed by global admins, so memberships were created by admins. `member_role` is removed from the API.

Project tokens (migration `026`): `auth_users` gains `kind` and `project_id`, `auth_tokens` gains `project_id`, `created_by` and `project_role`. Project tokens are not part of backups; reissue them after a restore.

Defaults for existing projects: hosted repositories only, all formats, repository name prefix `<slug>-`, at most 50 repositories, token TTL 365 days. These policies are stored now and enforced in later releases.

Breaking changes:

| Area | Change |
|---|---|
| API | `/api/v1/orgs*` is replaced by `/api/v1/projects*` (members and new `groups` routes included); the list key is `projects`. The project API is no longer global-admin only: project owners and maintainers manage their own project, see [Projects](../security/projects.md). |
| API | **Verb change:** updating a project is `PATCH /api/v1/projects/{project}` and changing a member's role is `PATCH /api/v1/projects/{project}/members/{user_id}`; `PUT` on those two routes is no longer accepted, so clients written against the earlier projects API (including pre-release builds) must switch. Adding a member accepts `username` as well as `user_id`; `PUT`/`DELETE …/groups/{group}` takes a group id or exact name. A caller who is not a member of a project gets `404` on its routes, the same as for an unknown project. `GET /api/v1/projects` returns `my_role` per project and `can_create`, and a new setting `projects.self_create` (`OPENARTIFACT_PROJECTS_SELF_CREATE`, default off) lets any user create projects. |
| Repositories | The `org` field of repository responses and of `POST`/`PATCH` bodies is now `project`. |
| CLI | `oa org` is now `oa project` (new `groups`, `add-group`, `rm-group`; `add-member --role` takes `viewer\|developer\|maintainer\|owner`, default `viewer`; `add-member` also takes `--username`; new `update` and `set-role`, both sending `PATCH`). |
| Audit log | The `org_id` column/field is `project_id`. |

Project quotas and cleanup defaults:

| Area | Change |
|---|---|
| Quotas | A project can carry a storage quota (`PUT /api/v1/projects/{project}/quota`, global admin only) over the total of its repositories. An upload must fit the repository's limit and the project's (`507`), and a repository limit above the project limit is refused (`400 validation_failed`). Counters are maintained only while a project limit is set; reconcile repairs drift. Projects start unlimited, so nothing changes until an admin sets a limit. See [project quotas](../repositories/cleanup-and-quotas.md#project-quotas). |
| Projects | Transferring a repository moves its storage usage to the target project and fails with `409 project_quota_exceeded` when the target's quota cannot take it (usage counters were not moved before). `GET /api/v1/projects/{project}/usage` reports totals and a per-repository breakdown. |
| Cleanup | Projects can define default cleanup policies (`/api/v1/projects/{project}/cleanup-policies`), applied to hosted repositories without an enabled policy of their own. See [project default cleanup policies](../repositories/cleanup-and-quotas.md#project-default-cleanup-policies). |
| Web UI | Project page: new **Usage** section for all members; **Settings** gains the project quota (admin-editable) and the cleanup defaults. |

Backup archives written by older versions still restore: the old table names `organizations` and `organization_members` are accepted.

### 0.5.1

No migrations. Fixes a startup deadlock between replicas: a replica waiting for the migration lock could deadlock with one running a `CREATE INDEX CONCURRENTLY` migration (`deadlock detected`, `SQLSTATE 40P01`) and exit. Waiting replicas now poll the lock instead of blocking on it.

### 0.5.0

> **Before upgrading a multi-replica deployment:** stop every pre-0.5.0 replica before the new version starts (Kubernetes: `strategy: Recreate`, or scale to 0 first). Migrations `018`, `019` and `022` change unique indexes and tables that older binaries write to, so old and new replicas cannot run side by side. The runtime image no longer contains a shell: with Helm chart 0.1.4 or older set `database.waitForDatabase=false` (the server waits for the database itself), or upgrade to chart 0.2.0.

> **Security: Go module repositories on 0.4.1 and earlier leak zips across repositories and projects.** Up to 0.4.1 the Go module upload stored every zip's database row without a digest, so all Go module versions of an instance shared one blob record that points at the **first** zip ever uploaded. Every `.zip` download in every Go repository, of any project, returned that one zip: a user who could read any Go repository could read the source of the first module published anywhere on the instance. **Upgrade, then check your Go repositories.**
>
> - Affected: every Go repository whose versions were uploaded on **0.4.1 or earlier**. Versions uploaded after the upgrade are not affected.
> - **Fail closed:** the new version answers `404` for any Go module zip whose blob has no valid sha256 and logs `refusing to serve go module zip ... re-upload the version or run the gomod repair` (repository, module, version). Nothing is served from the shared record any more, even if the repair below cannot fix a row.
> - **Automatic repair:** at every start a background task, run by one replica at a time (PostgreSQL advisory lock), looks for Go versions (trashed ones included) that still point at such a record. If there are none it exits at once. Otherwise it recovers each real zip from the blob store (the zips of later uploads were stored under their true sha256 and never deleted), checks it (content matches its sha256, every entry under one `<module>@<version>/` prefix, its `go.mod` equals the stored one) and relinks the version to it. The shared record is then deleted from the database; its object is never deleted, because it is a real module's zip. A version that matches several different stored zips (for example two forks publishing the same module path and version) is **not** guessed: it stays unservable.
> - **Re-run on demand:** `openartifact-server -repair-gomod` runs one repair pass and exits (same configuration and environment as the server; `0` when everything was repaired, non-zero when versions remain). It prints a summary and lists every unrepairable `repository: module@version`; the same lines are logged as warnings at startup.
> - **Re-upload what could not be repaired.** Those versions keep answering `404`; delete them and `PUT` the zip again ([Go modules](../formats/go.md#publish)). On storage backends that cannot list objects (`oci`) only the zip of the shared record itself can be recovered, so all other affected versions must be re-uploaded.
> - **Backups taken on 0.4.1 or earlier:** their Go module records carry no zip digest, so restoring skips those versions (logged, and the restore reports as incomplete); re-upload them. Migration `021` adds a database check (`blobs_sha256_hex`) so a blob record without a 64-hex sha256 can no longer be written; it does not scan existing rows, so the repair can still replace them.
> - Treat the first module's source as having been disclosed to every user who could read any Go repository on the instance, and rotate anything sensitive in it.

Migration `016` runs automatically at first start (adds `repositories.presign_downloads` and the `presigned_uploads` table). Default behavior is unchanged: downloads still stream through the server until you opt in to presigned URLs ([storage](../operations/storage.md#presigned-urls)).

Migrations `017` and `018` run at first start: `017` adds the soft-delete columns (`deleted_at`, `deleted_by`) to the repository and per-format package tables and the per-repository `trash_retention_days` and `immutable_releases` settings; `018` turns the uniqueness constraints of those tables into partial unique indexes over live rows. Neither rewrites table data; see the locking notes in the table below. Behavior changes:

| Area | Change |
|---|---|
| Image base | The runtime image is now a shell-less hardened base (`dhi.io/static`, Debian 13): it has no `sh`, `wget`, `nc` or `apk`. It still runs as uid/gid 10001 with the binary at `/app/openartifact`; the health check is `openartifact-server -healthcheck` (a `GET` on `127.0.0.1:<configured port>/health`, exit 0 on 200). |
| Troubleshooting | Use `kubectl debug -it <pod> --image=busybox --target=openartifact` (an ephemeral container sharing the process namespace) or `docker run --rm -it --network container:openartifact busybox`; `exec` into the container no longer works. |
| Custom CAs | Mount the CA bundle into the container and point `SSL_CERT_FILE` (one file) or `SSL_CERT_DIR` (a directory) at it; `update-ca-certificates` cannot run in the image. |
| trivy / grype | The `trivy` and `grype` vulnerability scanner backends need those static binaries on the server's `PATH`; build a derived image `FROM` the release image that copies them in, or use the default `osv` scanner. |
| Helm chart | Chart `<= 0.1.4` runs a wait-for-database init container that needs `sh` and `nc` from this image and fails with the new image. Upgrade the chart, or set `database.waitForDatabase=false`: the server now waits itself, retrying the initial database connection with capped backoff for `DB_CONNECT_TIMEOUT` (`database.connectTimeout`, default `60s`, `0` fails immediately). |
| Database startup | New `DB_CONNECT_TIMEOUT` / `database.connectTimeout`: the server retries the first database connection for up to this long (each wait is logged at info level) instead of exiting at once. |
| Security (Go) | Go module zips are served only when their blob has a real sha256 (`404` otherwise), and every blob upsert (all formats) rejects a sha256 that is not 64 lowercase hex characters. Versions published on 0.4.1 and earlier are repaired automatically at start, or with `openartifact-server -repair-gomod`; see the security note above. |
| Config | `database.options` and `storage.options` now have env overrides, `DB_OPTIONS` and `STORAGE_OPTIONS` (comma-separated `key=value` pairs merged over YAML); `STORAGE_TYPE` is listed in `.env.example`. |
| Security (login) | The failed-login lockout is now per (username, client IP) instead of per username, so an attacker can no longer lock the real user out from another address. |
| Docker | Pushing a manifest whose config or layer blobs are not stored in the repository now fails with `400 MANIFEST_BLOB_UNKNOWN` instead of storing a manifest that cannot be pulled. |
| Docker | Blob visibility is now per image: an image can only `GET`/`HEAD`/`DELETE`, mount from or reference in a manifest blobs that were pushed to it, mounted into it or referenced by one of its manifests, so an RBAC `path_pattern` limited to one image no longer reaches other images' layers in the same repository. Migration `022` adds `docker_blob_images` and `docker_blobs.size_bytes` and links existing blobs through the manifests that reference them; images whose manifests are not indexed yet keep access to the repository's existing blobs until registry GC indexes them. Clients that push an image sharing layers with a sibling image of the repository re-send those layers once (or mount them with `from=`). Blob responses use the verified size and `Content-Type: application/octet-stream`. |
| Security (storage) | Every blob store (filesystem, S3/GCS, Azure, OCI) now verifies the `sha256` it is given against the streamed bytes before the object becomes visible and rejects a mismatch with `storage.ErrDigestMismatch`; an object that already exists is never overwritten. Docker upload sessions are serialised, so a `PATCH` racing the completing `PUT` can no longer change the stored bytes. |
| Docker | The shared `blobs` row keeps the first writer's `media_type` and corrects a recorded size of `0`; Go `.mod` and Cargo blobs record their real size. A manifest push re-checks its blobs under the registry GC lock. |
| API | `GET .../packages/{id}/delta` now also finds deb source packages and no longer scans the whole repository. MCP `list_ai_analyses` honors `license_concern`; MCP `search_artifacts` and REST search resolve readable repositories with one permission lookup. Removing a bundle item races safely with sealing (`409` if sealed). The OpenAPI spec documents the deb/rpm upload, delete, comps and delta routes and corrected schemas. |
| Config | New opt-in keys `storage.presignDownloads`, `presignMinSize`, `presignEndpoint`, `presignUploadTtl`, `presignMaxPendingUploads` (default 20 outstanding uploads per user, `0` = unlimited; env `STORAGE_PRESIGN_*`). `presignTtl` (`STORAGE_S3_PRESIGN_TTL`) now takes effect: it is the lifetime of presigned download URLs, clamped to 1 m - 1 h. A negative `presignMinSize` stops startup. |
| Downloads | With `presignDownloads` on (s3 and gcs backends), blob downloads of every format answer `307` with a presigned URL; metadata is still streamed. Per-repository override `presign_downloads` (`true`, `false`, `null` to inherit) on the repository API and in the repository Settings tab. |
| API | New `POST /api/v1/repositories/{name}/uploads` and `POST /api/v1/repositories/{name}/uploads/{id}/complete` for presigned raw uploads (s3 and gcs backends; `501` elsewhere). RBAC treats them as repository write; only the creator or an admin can complete an upload, and `complete` is idempotent. |
| CLI | `oa artifact upload --presigned` uploads a raw file straight to the object store; the server then reads it back to verify the sha256. |
| Metrics | New counter `openartifact_blob_downloads_total{mode,reason}`. |
| Caveats | Set `presignEndpoint` when `endpoint` is a cluster-internal address clients cannot reach. Clients must reach the object store host directly. The object store answers with `Content-Disposition: attachment; filename="..."`. ivy and sbt clients do not follow redirects across schemes: set `presign_downloads` to `false` on those repositories unless the store uses the same scheme. A worker removes abandoned presigned-upload staging objects; a bucket lifecycle rule expiring the `staging/` prefix after 1-2 days is recommended as defence in depth. |
| SSO (SAML) | The IdP metadata URL is fetched through the outbound SSRF guard (1 MiB cap, 10 s timeout). Metadata URLs on private or loopback addresses need `OPENARTIFACT_ALLOW_PRIVATE_UPSTREAMS=true`. |
| SSO (SAML) | Signed responses or assertions with more than 1000 XML elements (large group lists) are accepted again; SAML now uses the `openartifact/saml` fork of crewjam/saml. |
| Migration locks | `017` runs in one short transaction: metadata-only `ADD COLUMN` on `repositories` and the 17 per-format package tables, and the `audit_logs` action constraint re-created `NOT VALID` (no table scan; new actions are accepted immediately). It holds `ACCESS EXCLUSIVE` locks only for that moment, whatever the table sizes, and gives up (rolls back; the next start retries) if a lock is not granted within 10 s, rather than queueing every query behind a long-running one such as a backup. |
| Migration index builds | `018` runs without a transaction. Per table it builds the live-row unique index and the `idx_<table>_deleted` index with `CREATE INDEX CONCURRENTLY` (reads and writes continue; the time is proportional to the table size, and instant on an empty database), then drops the old unique constraint (an `ACCESS EXCLUSIVE` lock for an instant, abandoned after 10 s and retried at the next start). Uniqueness is enforced at every step. It ends with `VALIDATE CONSTRAINT chk_audit_action`, which scans `audit_logs` under `SHARE UPDATE EXCLUSIVE` and does not block inserts. The server serves requests only once the migrations are done (other replicas wait on the migration lock), so on a very large database run `./openartifact -migrate` ahead of the rollout ([migrating separately](#migrating-separately-from-the-rollout)). A `018` that was interrupted or failed is safe to re-run: indexes left invalid by a cancelled build are dropped and rebuilt, finished steps are skipped. Long transactions (a running `pg_dump`) delay `CREATE INDEX CONCURRENTLY`; schedule the upgrade outside the backup window. |
| Rolling upgrade | Stop the old replicas before the new version migrates. Once `018` has dropped the old unique constraints, a previous version's upserts (`ON CONFLICT (...)` without the `WHERE deleted_at IS NULL` predicate) on raw, maven, nuget, docker manifests and docker tags fail with SQLSTATE `42P10`, and old binaries do not hide trashed rows. Between `017` and `018` the old constraints still hold, so a previous version keeps working. |
| Deletes | Soft by default. Deleting an artifact, version, tag or repository moves it to the [trash](../operations/trash.md) for 7 days (`OPENARTIFACT_TRASH_RETENTION` / `trash.retentionDays`) instead of destroying it; a background purge removes it afterwards (`OPENARTIFACT_TRASH_PURGE_INTERVAL`, default `15m`). Set `OPENARTIFACT_TRASH_RETENTION=0` for the previous immediate behavior, or `trash_retention_days` per repository. |
| Repository delete | `DELETE /api/v1/repository/{name}` needs a confirmation: `?confirm=<name>` or a JSON body `{"confirm":"<name>"}`, otherwise `400 confirmation_required`. The CLI takes `oa repo delete <name> --confirm <name>` (prompts on a terminal, fails without `--confirm` otherwise). Update scripts that delete repositories. |
| API | New endpoints `GET /api/v1/trash`, `GET /api/v1/repositories/{name}/trash`, restore (`POST .../restore`) and purge (`DELETE /api/v1/trash/{kind}/{id}`); repository create/update/read gain `trash_retention_days` and `immutable_releases`. |
| Immutable releases | New per-repository `immutable_releases` option (default off): deleting or overwriting a released version is `409` unless an admin passes `?force=true`. Cleanup policies never remove released versions of such repositories. |
| Webhooks and audit | New events `artifact.restored`, `artifact.purged`, `repository.restored`, `repository.purged`. `artifact.deleted` and `repository.deleted` also fire for soft deletes. Review webhook subscriptions that treat `*.deleted` as "bytes are gone". |
| Quotas | Soft-deleted bytes keep counting against a repository's quota (and the quota reconcile counts them) until the item is purged. |
| Repository names | The name of a repository in the trash stays reserved: creating a repository with it is `409` until the old one is purged or restored. |
| Storage | Blobs of trashed items are kept; disk usage drops only when the purge worker runs. [Docker GC](../formats/docker.md#garbage-collection) does not collect trashed manifests. |
| Backups | Items in the trash are not included in backups (a backup holds live data only). |
| Repository names | Creating a repository named `new`, `settings`, `trash`, `raw`, `maven`, `sbt` or `ivy` (case-insensitive) is `400 validation_failed`: they collide with web UI routes and isolated format URL namespaces. Existing repositories with those names are not touched (see [repositories](../repositories/hosted-proxy-group.md)). |
| Web UI | Deep links (reload, bookmark, new tab) now work for package pages whose name contains `/` (scoped npm, docker, go modules) and for `/repos/<name>/settings` (opens the repository's Configuration tab). The package "Properties" tab shows stored properties. Package pages and the security scan pickers look packages up on the server instead of loading at most 2000 rows. Row and bulk delete buttons appear only for deb and rpm repositories (the only formats the server can delete by id). "Empty trash" shows and offers the repository's full trash count regardless of the kind filter. The unused Notifications settings page was removed. |
| API | `GET /api/v1/repositories/{name}/packages` accepts `package_name` (exact listed name) next to `format`. |
| CLI | `oa webhook create` and `oa webhook repo create` no longer accept `--secret` (visible in `ps`); use `--secret-file FILE` (`-` for stdin) or `OA_WEBHOOK_SECRET`. `oa auth logout --revoke --username U --password-stdin` also revokes the saved server-side token. A corrupt `config.json` no longer blocks `oa auth login`, `help` and `version`. `oa import` resumes assets without a source SHA-256 (falls back to SHA-1, then size). |
| CLI | New `oa trash list|restore|purge`; `oa repo create|update` accept `--trash-retention-days` and `--immutable-releases`. |
| Security (proxies) | `X-Forwarded-For` is read right to left and the first hop that is not in `trustedProxies` is the client IP (before: the leftmost entry, which a client could forge). Rate limits, the IP allowlist, login throttling and audit now see the real client. `X-Real-IP` is honored only when it is not itself a trusted proxy. |
| Security (IP allowlist) | `ipAllowlist` accepts bare IPs as well as CIDRs, and an unparsable entry now stops startup instead of silently disabling the allowlist. |
| Security (raw/artifact downloads) | All `/repos/...` responses carry `Content-Security-Policy: sandbox; default-src 'none'`, and HTML, SVG, XML and other actively rendered types are served with `Content-Disposition: attachment` (stored XSS fix). Browsers download instead of rendering such files. |
| Security (users) | A non-admin can no longer change their own `email` (`PATCH /api/v1/users/{id}` returns `403`); admins still can. This closes pre-claiming a victim's address to be linked by SSO `link_by_email`. |
| Security (CSRF) | Basic-token requests carrying `Sec-Fetch-Site: cross-site/same-site` or a foreign `Origin` now need the CSRF token like session requests. CLI clients are unaffected. |
| Sessions | The session and CSRF cookies' `Max-Age` is the absolute session lifetime (30 days) instead of the 24 h idle window, so the sliding expiry works for active users. |

## Rollback

Because migrations are forward-only, going back to an older version after a migration has run means restoring the database backup taken before the upgrade, then starting the older version. An older binary does not refuse a database with newer migrations (it only checks the migrations it knows), but a newer schema is not guaranteed to work with it. Restore the blob store snapshot that matches the database backup if artifacts were uploaded or deleted in between.
