# Upgrading

Upgrade by replacing the binary or image; the database schema is migrated forward automatically at startup.

Checklist:

1. Read the release notes on the [GitHub releases page](https://github.com/openartifact/openartifact/releases) (generated by GoReleaser from the git history, grouped into Features, Bug fixes, CI and build, Other).
2. Back up the database and blob store ([backup](../operations/backup.md)) and make sure the [secrets](#secrets-to-preserve) are stored safely.
3. Deploy the new version ([Docker Compose](#docker-compose), [Helm](#helm), [binary](#binary)).
4. Check `GET /health`: the JSON `version` field shows the running version and `status` should be `healthy`.

## Versions and image tags

- The `VERSION` file at the repository root is the release version. Releases are cut from tags `vX.Y.Z`; the release workflow fails unless `VERSION` equals the tag without the `v`. A tag containing a `-` (for example `v1.0.0-rc.1`) is a pre-release.
- Images are published to `ghcr.io/openartifact/openartifact` for `linux/amd64` and `linux/arm64` with tags `X.Y.Z` (no `v`) and `X.Y`; `latest` is only moved by tags without a pre-release suffix. Pin an exact `X.Y.Z` in production.
- Release archives (`openartifact_<version>_<os>_<arch>.tar.gz`, `oa_...`) and `SHA256SUMS` are attached to the GitHub release; see [installation](installation.md#release-archives) and [signing](../security/signing.md) to verify them.
- A binary built without `-ldflags` reports version `dev`. The compose file builds from the checkout and takes the version, commit and build time from `OPENARTIFACT_VERSION`, `OPENARTIFACT_COMMIT` and `OPENARTIFACT_BUILD_TIME` (defaults `dev`, `unknown`, `unknown`); `make docker-up` fills them from the `VERSION` file and git. `openartifact-server -version` prints what a binary was stamped with.

## Database migrations

- Migrations are SQL files embedded in the binary (`migrations/`) and applied in file-name order. Applied versions are recorded in the `schema_migrations` table (`version`, `applied_at`, `checksum`, the SHA-256 of the file).
- They run automatically at every start unless `MIGRATE_ON_START=false`, under a PostgreSQL advisory lock, so several replicas can start at once and only one applies each migration. Each file runs in its own transaction; files named `*.no_tx.sql` run without one, one statement at a time (needed for `CREATE INDEX CONCURRENTLY`, which cannot run in a transaction).
- **Forward-only.** There are no down migrations. An applied file must never change: if the checksum of an applied migration differs from the one in the binary, the migrator aborts with a `checksum drift` error instead of continuing.
- A failed migration is rolled back (transactional files) and the server logs `auto-migrate failed` and exits with status 1.
- Running a new binary against an old database applies the pending migrations; there is no dry-run mode.

### Migrating separately from the rollout

Set `MIGRATE_ON_START=false` (the exact lowercase string; other values keep migrations on) and run the migrations as a one-off step before starting the new version, with the same database settings:

```sh
./openartifact -migrate                     # binary: applies migrations and exits
docker compose -f docker/docker-compose.yml run --rm openartifact ./openartifact -migrate
```

With `MIGRATE_ON_START=false` the server logs `automatic migrations skipped` at start and does not check the schema version, so a new binary against an unmigrated database may fail at query time. `make migrate` does the same from a source checkout (`go run ./cmd/server -migrate`).

### Unreleased

- Maven poms that declare no license now inherit it from their `<parent>` pom stored in the same repository or in a group it belongs to (including poms a proxy member already cached), for the upload license policy, the license scan and the SBOM. A blocking policy can therefore reject a child whose parent declares a denied license. Existing scan results are not rewritten: scan the pom again. See [Maven parent poms](../security/licenses.md#maven-parent-poms).

## Docker Compose

From the checkout of the new version:

```sh
git fetch --tags && git checkout vX.Y.Z
make docker-up    # same as docker compose -f docker/docker-compose.yml --env-file docker/.env up -d --build, plus build metadata
```

This rebuilds the `openartifact` image and recreates the container; the named volumes (`postgres_data`, `artifacts_data`, `backups_data`) are kept. `docker compose down -v` deletes them, do not use it for an upgrade. Migrations run when the new container starts. To run a released image instead, point the service at `ghcr.io/openartifact/openartifact:<version>` and use `docker compose pull && docker compose up -d`. The compose file pins the PostgreSQL major version (`postgres:18-alpine`); it is not changed by an OpenArtifact upgrade.

## Helm

The chart is versioned separately from the application (the chart `version` and `appVersion` differ). The image tag defaults to the chart's `appVersion`; override with `image.tag`.

```sh
helm upgrade openartifact oci://ghcr.io/openartifact/charts/openartifact \
  --namespace openartifact -f my-values.yaml
# classic repository: helm repo update && helm upgrade openartifact openartifact/openartifact -n openartifact -f my-values.yaml
```

- Pods apply migrations at startup (`config.migrateOnStart`, default `true`) under the advisory lock. During a rolling update, old pods keep running against the already-migrated schema until they are replaced; nothing in the project guarantees that an older version works with a newer schema.
- With a single `ReadWriteOnce` volume the Deployment uses `Recreate`, so an upgrade has a short downtime. Object storage or `ReadWriteMany` allows rolling updates.
- The generated Secret (`AUTH_HMAC_KEY`, `OPENARTIFACT_SECRET_KEY`) is reused on upgrade through Helm's `lookup`. That does not work under `helm template`: with Argo CD or similar, create the Secret yourself and set `secrets.existingSecret`. Option reference and details: [chart README](https://github.com/openartifact/helm-charts/blob/main/charts/openartifact/README.md).

## Binary

Stop the old process, replace the `openartifact` binary (and `resetpw`) with the new release, then start it with the same configuration. Run `./openartifact verify openartifact.yaml` first to catch configuration errors; compare your file against the new `openartifact.example.yaml` and root [`.env.example`](../../.env.example) for added keys ([configuration](configuration.md)).

## Secrets to preserve

Keep these identical across upgrades, restores and replicas:

| Setting | If lost or changed |
|---|---|
| `OPENARTIFACT_SECRET_KEY` | Values stored encrypted (`enc:v1:...`: webhook secrets, upstream passwords, SSO client secrets, AI keys, storage credentials) can no longer be decrypted. Removing the key entirely makes reading them fail; setting it for the first time leaves existing plaintext values readable |
| `AUTH_HMAC_KEY` | Signs OIDC/SAML login state. If unset, a random key is generated at every start; logins in flight during a restart, or handled by a different replica, fail. Sessions and API tokens are not affected |
| `OPENARTIFACT_SAML_SP_CERT` / `_KEY` | Without them an ephemeral keypair is generated per process; the IdP registration must be redone after each restart |
| `BASE_URL` | SAML entity ID and ACS URL, and links in generated indexes, are derived from it; changing it breaks existing IdP registrations |

Docker Compose only passes `AUTH_HMAC_KEY` through; see [installation](installation.md#docker-compose) for adding the others. The `docker/.env` file and any compose override belong in your backup.

## Version notes

### Unreleased

- Cleanup policies now run on every hosted format (npm, maven, ivy, sbt, cargo, rubygems, conda, conan, raw and docker join deb, rpm, helm, pypi, nuget and go). Policies already stored for these formats, which used to fail on every run, now execute on their next schedule: review their `keep_*` settings, or use the new `POST /api/v1/repositories/{repo}/cleanup-policies/{id}/dry-run` to see what a run would remove. Quarantined packages are now also skipped by cleanup for every format. See [cleanup policies](../repositories/cleanup-and-quotas.md#supported-formats).
- `DELETE /api/v1/repositories/{repo}/packages/{id}` now works for every hosted format (it answered `400 UNSUPPORTED_FORMAT` for all but deb and rpm); the web UI offers package delete for all of them. Rows go to the [trash](../operations/trash.md) when the repository keeps one.
- SPDX `documentNamespace` and OpenVEX `@id` are now minted under `BASE_URL` (`urn:openartifact:...` when it is empty) instead of `openartifact.io`. Documents already stored keep their identifiers.
- Creating or updating a cleanup policy on a repository whose format the cleanup worker cannot process now answers `400 UNSUPPORTED_FORMAT`; such policies previously failed on every run.
- `POST /api/v1/admin/storage/{name}/test` runs a real bucket or container check for `gcs` and `azure` backends instead of answering `not_implemented`.
- SBOM components are now read from the stored package file (manifest and lockfile) for npm, pypi, maven, sbt, ivy, cargo, go, nuget, rubygems, helm, conda, deb, rpm and conan, and merged with the `dependencies` property. SBOMs generated after the upgrade list more components than before. `artifact_id` may also be a package-listing row id. `POST …/sbom/generate` answers `422 unsafe_artifact` for a package file that cannot be read safely. See [SBOM and VEX](../security/sbom.md#components-read-from-the-package-file).
- The web UI can record, list and delete VEX decisions and download OpenVEX / CycloneDX VEX documents (Security → Vulnerability scans).
- `POST /api/v1/bundles/{name}/{version}/promote` now promotes: it copies every item of a sealed bundle into the target repository and records the promotion, instead of answering `501 not_implemented`. Clients that treated the `501` as "feature unavailable" must handle `200`, and the new `409`/`403`/`507` outcomes ([Release bundles](../repositories/release-bundles.md#promoting-a-bundle)). Administrators can pass `?force=true` to replace conflicting content in the target. Webhooks and SIEM integrations can subscribe to the new `bundle.promoted` event.
- Migration `058` adds three tables (additive): two for the Dependency-Track integration and the per-repository switch for attaching attestations to docker images.
- **Signed SBOM and VEX.** `GET …/sbom/{id}/download` and `GET …/vex` accept `?attest=true` (a DSSE envelope, in-toto attestation) or `?attest=bundle` (a Sigstore bundle that `cosign verify-blob-attestation` reads). The key is `attestation.keyPath` (`ATTESTATION_KEY_PATH`) or, when unset, an ECDSA P-256 key generated on first use and stored encrypted in `system_settings`; its public half is at `/.well-known/openartifact/attestation-key.pem`. Nothing changes for existing callers. See [SBOM and VEX](../security/sbom.md#signed-sbom-and-vex-attestations).
- **SPDX 3.0.1** JSON-LD: `format` `spdx3-json`.
- **Dependency-Track.** An admin-configured integration (global, with per-repository overrides) pushes the CycloneDX BOM on upload and after each scan, then the VEX decisions after Dependency-Track's analysis. It is off until configured: nothing leaves the server by default. The URL goes through the same SSRF guard as other outbound requests, so a Dependency-Track on a private address needs `OPENARTIFACT_ALLOW_PRIVATE_UPSTREAMS=true`. See [Dependency-Track](../security/dependency-track.md).
- **Attestations as OCI referrers.** A hosted docker repository can attach the signed SBOM and VEX of an image to it as OCI referrers (`POST …/sbom/{id}/attach`, `POST …/vex/attach`, or automatically after SBOM generation and scans with `PUT …/attestation-attach`). Off by default. See [Attaching to an OCI image](../security/sbom.md#attaching-to-an-oci-image).
- `oa dtrack`, `oa sbom download --attest` and `oa vex get --attest`.

#### Conan 1.x clients (migration `057`)

A Conan 1.x client can now use a conan repository (see [Conan](../formats/conan.md#conan-1x)). Migration `057` adds `md5` and `sha1` columns to `conan_packages` and an index on `sha1` (`CREATE INDEX CONCURRENTLY`); it also stops the `updated_at` trigger from firing on a digest-only change, because that column is the revision time. The migration is additive and safe for a rolling upgrade.

- Files stored by earlier versions have no digests. A Conan 1 client's file listing fills in the MD5 on first read; the SHA-1 is recorded then too. Those files only take part in checksum deploy after that, or after being uploaded again.
- The ping now advertises `revisions,checksum_deploy`. Conan 2 clients start sending an empty `PUT` with `X-Checksum-Deploy: true` before uploads and fall back to the normal upload on `404`; nothing to change on the client.
- Set `BASE_URL` to the address clients use: Conan 1 URLs in `upload_urls` and `download_urls` are absolute.

#### Docker catalog, trashed blobs, proxy digest eviction (migration `063`)

- `GET /v2/_catalog` now exists: it lists the docker images the caller may read, paginated with `n`/`last`. See [Docker](../formats/docker.md#endpoints).
- A layer or config blob that only trashed manifests reference now answers `404 BLOB_UNKNOWN` by digest until a manifest that references it is restored. Before, it stayed downloadable while the image sat in the trash.
- Docker proxy repositories used to keep manifests and blobs addressed by digest forever. They are now evicted after `workers.proxyDockerDigestTtl` (default `720h`, env `OPENARTIFACT_PROXY_DOCKER_DIGEST_TTL`) without a pull, and a pull renews them; the next pull of an evicted digest goes to the upstream again. Set it to `0` to keep the old behavior. Migration `063` gives the entries already cached the default 30 days from the upgrade, so content nobody pulls in that time is evicted by the proxy cache worker.

#### GPG key management (migration `054`)

Migration `054` (GPG key management; additive) creates `gpg_keys` and `gpg_key_repositories` and widens the `chk_audit_action` constraint with the `gpg_key.*` audit actions (`NOT VALID`, then validated by `054_gpg_keys_validate.no_tx.sql`). A rolling upgrade is fine.

- **GPG keys are managed at runtime.** `/api/v1/admin/gpg/keys`, `oa gpg` and the **Admin → GPG keys** page now work (they were stubs). A key configured with `gpg.keyPath` keeps signing exactly as before and appears as a read-only `config` entry; a key you activate takes precedence over it. Storing keys requires `OPENARTIFACT_SECRET_KEY`; without it the page shows how to enable it.
- **`gpg.autoGenerate` now works.** With no key configured and none stored, the first start generates an RSA-4096 key (global, active) and logs its fingerprint. It needs `OPENARTIFACT_SECRET_KEY`; without it a warning is logged and nothing is generated. It was a no-op before, so an existing `GPG_AUTO_GENERATE=true` starts producing a key on upgrade.
- **APT repositories serve `public.key`.** `HOST/repos/REPO/public.key` used to return `404` for Debian repositories; it now returns the key that signs the repository, from the next metadata regeneration (or when a key is activated).
- **RPM `primary.xml` lists packages under `<location>`** (it was written as `<Location>`, which dnf cannot download from). Fixed; repositories pick it up when their metadata is next regenerated (any upload or delete, or a key change).
- **Bundles can be sealed with a GPG signature** (`gpg_key_id`, previously `501`), with `GET .../manifest` and `.../manifest.asc` to verify it.
- **RPM repositories can sign packages.** Migration `054` also adds `repositories.sign_packages` (default `false`, so nothing changes on upgrade). Enabling it on a hosted RPM repository signs every later upload with the repository's signing key, so dnf works with the default `gpgcheck=1`; the stored file is the signed one (new SHA-256), existing packages are not re-signed and key rotation does not touch them ([RPM](../formats/rpm.md#signing-packages-sign_packages)). Debian needs no change: apt trusts the signed `Release`.

- **Deb and RPM group repositories** can now be created. Migration `059` adds `group_metadata_state` and `group_package_owners` (and one `CREATE INDEX CONCURRENTLY`); it is additive and a rolling upgrade is fine. Groups of these formats generate their metadata at startup for groups that have none, and when members change; see [Deb and RPM groups](../repositories/hosted-proxy-group.md#deb-and-rpm-groups) for what is merged, signing and access control.

#### Multipart and universal presigned uploads (migration `056`)

- Migration `056` adds `part_size` and `multipart_id` to `presigned_uploads`. It is additive; a rolling upgrade is fine.
- **Presigned raw uploads work on every storage backend** and files above 5 GiB (up to 5 TiB) are uploaded in parts: `POST /api/v1/repositories/{name}/uploads` takes `multipart` and `part_size`, `.../uploads/{id}/parts` signs part URLs and `.../uploads/{id}/abort` discards an upload. `oa artifact upload --presigned` switches to multipart above 5 GiB (`--multipart`, `--part-size`, `--parallel`). A size above 5 GiB without `multipart` is refused with `400 invalid_size`. See [Presigned uploads](../operations/storage.md#presigned-uploads).
- Azure gets SAS URLs for uploads and (with `presignDownloads`) downloads, and a new `azureEndpoint` / `OPENARTIFACT_AZURE_ENDPOINT` for Azurite or sovereign clouds.
- Filesystem and OCI storage serve the upload themselves through `PUT /upload-relay/{id}/{part}` with a short-lived HMAC-signed URL. It is built from `baseUrl`, so set `BASE_URL` to an address clients can reach; without it the create call still answers `501 presign_unsupported`. The filesystem backend keeps its staging data in `<path>/staging` (never listed as blobs); OCI spools in `stagingPath` / `STORAGE_STAGING_PATH`.
- `complete` timeouts now scale with the object size (30 minutes plus one second per 20 MiB, at most 6 hours), and promoting an S3 object above 4 GiB uses ranged `UploadPartCopy`.
- Add an `AbortIncompleteMultipartUpload` lifecycle rule (2 days) to the bucket as defence in depth; the cleanup worker aborts abandoned multipart uploads itself.

#### Release bundles in the web UI

- New admin pages **Release bundles** (`/bundles`, `/bundles/{name}/{version}`): list and filter bundles, create drafts, add and remove items, seal (optionally signing the manifest with a GPG key), promote a sealed bundle to the next pipeline stage, archive, delete drafts, and download the manifest and signature. No API, schema or configuration change. See [release bundles](../repositories/release-bundles.md#web-ui).

### 0.7.0

Migrations `041` (scan overview index, `CREATE INDEX CONCURRENTLY`), `051` (webhook payload format), `052` (VEX statements) and `053` (license source and unresolved licenses). All are additive; a rolling upgrade from 0.6.0 is fine. Migration `041` is numbered below `051`–`053` on purpose; the migrator applies every file not yet recorded, whatever its number.

#### License policies read the package itself (migration `053`)

- Licenses now come from the uploaded file (wheel `METADATA` / sdist `PKG-INFO`, npm `package.json`, Cargo `Cargo.toml`, NuGet `.nuspec`, Maven `.pom`; RubyGems already did). Upload form fields are only a fallback, so a client can no longer bypass a license policy by omitting or faking them. See [licenses](../security/licenses.md).
- **Under an enabled `block` policy, an upload whose licenses cannot be read from the file is refused** with `422 LICENSE_METADATA_UNREADABLE` (for example a PyPI `.egg`/`.exe`, a damaged archive, an unparsable `.pom`). A re-scan of such a stored package fails with `422 unreadable_artifact`. Without a block policy the client-declared fields stay the fallback.
- Scan results gain `license_source` (`artifact` or `client_declared`; existing rows read as `client_declared`) and `unresolved_licenses` (names such as `BSD` that do not map to one SPDX id). Existing results are not rewritten: re-scan to refresh them.

#### SBOM and VEX (migration `052`)

- SBOMs default to CycloneDX 1.5 (1.4 and 1.6 via `spec_version`) with purls, hashes, SPDX license expressions, the dependency graph and vulnerabilities; SPDX 2.3 is available as `spdx-json` and tag-value. Old `format` / `spec_version` values still work.
- New VEX documents (OpenVEX 0.2.0, CycloneDX VEX) and admin-recorded `not_affected` decisions: `GET /api/v1/repositories/{name}/vex`, `GET`/`PUT …/vex/statements`, `DELETE …/vex/statements/{id}`; `oa vex`. Decisions are included in backups. See [SBOM and VEX](../security/sbom.md).

- Audit exports: `GET /api/v1/admin/audit/export` and `GET /api/v1/projects/{p}/activity/export` (`jsonl` or `csv`), `oa audit export`. The field sets are an append-only contract. See [monitoring](../operations/monitoring.md).
- New cross-repository scan overview for admins: `GET /api/v1/vuln/scans` and `GET /api/v1/vuln/scans/summary`.

#### OpenTelemetry

- Optional OTLP tracing (and OTLP push of the Prometheus metrics), **off by default**: `OPENARTIFACT_OTLP_ENABLED=true` plus the standard `OTEL_EXPORTER_OTLP_*` variables. Inbound `baggage` is never forwarded to upstreams, webhooks or AI providers. The server binary is about 14 MB larger. See [monitoring](../operations/monitoring.md).

#### Docker Compose and the web UI

- The compose file no longer sets `container_name`; containers are named by the compose project (`docker-openartifact-1`, …). Scripts that address `openartifact` / `openartifact-postgres` by name must use `docker compose exec openartifact …` instead. The published port is `OPENARTIFACT_PORT` (default `8080`).
- The web UI is an installable app (web manifest and a service worker that caches only the hashed static assets, never API or repository responses). It needs HTTPS (or `localhost`); a reverse proxy must pass `/sw.js` and `/manifest.webmanifest` through without long-lived caching. See [installation](installation.md).

#### Prometheus `path` label

- The `path` label of `openartifact_http_requests_total` and `openartifact_http_request_duration_seconds` was always `unknown` (the middleware could not see the matched route). It now holds the route pattern (`/api/v1/repositories/{name}`, trailing `/*` removed), and `unmatched` for requests that match no route. Dashboards and alerts that select `path="unknown"` must be updated; series cardinality stays bounded by the route table.

#### Search ranking, grouping and the command palette

- **`GET /api/v1/search` no longer returns the `results` key.** It was a copy of `packages` kept from before 0.5.0; read `packages`. `oa search` is updated and its own `--format json` output keeps `results`.
- Results are ordered by relevance, then newest first: an exact name match, then names starting with the query, then other substring matches, with the row id as the last tie-break so paging is stable. Repositories are ranked the same way, then by name. Before, the order was the newest first only.
- New query parameter `group=package` returns one hit per package (its latest version) and counts packages in `total`. The command palette uses it. Without it nothing changes except the order.
- Migration `040` builds a trigram index on `repositories.name` (`CREATE INDEX CONCURRENTLY`, re-runnable, same `pg_trgm` requirement as migration `030`). It is numbered 040 on purpose, so migrations 035 to 039 stay free for changes prepared in parallel; the migrator orders by file name only, so the gap is harmless.
- The set of repositories a user may read is cached per user for `DB_AUTH_CACHE_TTL_MS` and dropped by the same writes that clear the auth cache, so a permission change made through this instance applies at once and one made through another replica within the TTL; see [Auth lookup cache](../operations/performance.md#auth-lookup-cache). `0` disables it.
- Creating a repository now clears the auth cache too, so a new repository shows up in permission-derived lists at once.
- Web UI: the Ctrl+K palette tells a too broad query ("Refine your query") from a failed request (inline error with Retry) and from an empty result, cancels the request of an outdated query, lists a package once, and links to `/search?q=…` for all results. The header trigger is a real button and shows ⌘K on Apple platforms, Ctrl K elsewhere. The duplicate "Open profile" command is gone ("Open settings" opens the same page).

#### Storage tiers (migration `032`)

Migration `032` adds `blobs.last_accessed_at` and `blobs.tier_changed_at` (nullable, no rewrite), the tables `storage_tiers`, `storage_policies` and `storage_tier_moves`, and seeds the tier `hot`, which is the configured primary store. `032_storage_tiers_indexes` builds an index with `CREATE INDEX CONCURRENTLY` (re-runnable); migration `034_blobs_tier_promote_index` replaces it with the ordered partial index `idx_blobs_tier_promote` (also concurrent, re-runnable) that serves promote-on-read, and drops the old `idx_blobs_tier_reads`. Reads are recorded only while a cold tier exists. Nothing moves until you add a tier and a policy: with only `hot` the mover is a no-op and every blob keeps its placement. Download times start being recorded after the upgrade, so an idle-based policy treats older blobs as "idle since creation". New settings: `tiering.*` ([configuration](configuration.md)). See [storage tiers](../operations/storage-tiering.md).

#### Consistent backups and deferred blob deletion (migration `035`)

Migration `035` adds the tables `blob_deletions` and `backup_leases` (no rewrite of existing tables). Behaviour changes:

- `full` backups read all records from one database snapshot and the blobs from the `blobs` table of that snapshot instead of listing the store, so they work on S3, GCS, Azure and OCI too. A backup holds a database transaction and up to five connections while it runs; keep `idle_in_transaction_session_timeout` off or longer than your longest backup. The manifest gains `snapshot_at` and `blob_count`.
- Deleting a blob no longer removes its bytes at once: they are queued and removed by a sweeper after `blobDeletion.grace` (default `24h`) and once no running backup needs them. Disk and bucket usage therefore fall up to a day after a delete or purge. Set `OPENARTIFACT_BLOB_DELETION_GRACE=0` to remove bytes as soon as no backup needs them. The same applies to the old copy left by a storage tier move.
- New settings: `backup.leaseTtl`, `blobDeletion.grace`, `blobDeletion.sweepInterval`, `blobDeletion.sweepBatch` ([configuration](configuration.md)).
- Mixed versions during a rolling update: an older replica still deletes bytes at once, so run no full backup until every replica runs this version.

#### Database indexes and the `pg_trgm` extension

Migration `030` needs the PostgreSQL `pg_trgm` extension (`CREATE EXTENSION IF NOT EXISTS pg_trgm`). It is a trusted extension since PostgreSQL 13, so the database owner can create it; it ships in the official `postgres` images and in the `postgresql-contrib` package of distributions that split it. On a managed service, allow-list it first, or run `CREATE EXTENSION pg_trgm` as an administrator before the upgrade. Without it the migration fails and the server exits at startup.

What changes:

- The transactional part creates the extension; the no-transaction part `030_perf_indexes_build` builds the indexes with `CREATE INDEX CONCURRENTLY` (reads and writes continue; on a very large database the trigram indexes take minutes). A build interrupted midway leaves an invalid index that the next start drops and rebuilds.
- New: `(repository_id, filename)` indexes on `deb_packages`, `rpm_packages` and `pypi_packages` (pool and file downloads were sequential scans), a partial expression index for PyPI names stored with `--`, 16 trigram indexes behind package search, and indexes for the foreign keys `deb_packages.component_id`, `auth_user_groups.group_id` and `repository_group_members.member_repo_id`.
- Dropped: the duplicate indexes `idx_blobs_sha256`, `idx_proxy_cache_repository_key` and `idx_vuln_results_scan_job`, which a unique or primary index already covers.
- The proxy cache eviction and the retention cleanup now work in batches (2000 expired cache entries, 200 package versions per round trip), so one long run no longer rolls back as a whole when it hits its timeout.
- `GET /api/v1/search` answers from one query (total and page together). Behavior is unchanged: a query matching more than 10000 rows is still `400 query_too_broad`.

#### Groups hide proxy versions of hosted package names

Migration `029` adds `repositories.merge_proxy_versions` (`boolean NOT NULL DEFAULT false`).

**Existing groups get the new default (hosted members win), which changes what merged views show.** For a package name that a readable hosted member holds, the versions, metadata entries and files that proxy members offer under that name disappear from the group (npm, pypi, go, cargo, nuget, maven, helm, docker; raw is unchanged). Names no hosted member holds are unaffected. This closes a dependency-confusion path: a public package with the same name as an internal one could previously add a higher version to the group. To restore the union for a group, an administrator sets `merge_proxy_versions=true` (`PATCH /api/v1/repository/{name}`, or the repository's settings page); see [hosted members win](../repositories/hosted-proxy-group.md#hosted-members-win-a-package-name).

Proxy repositories:

- Changing a proxy's `upstream_url` origin (scheme, host, port) or `upstream_username` in a `PATCH` clears the stored `upstream_password` unless the same request sends a new `upstream_password`. Update credentials together with such changes.
- The `Authorization` header is dropped on any redirect that changes scheme or host, and the outbound (SSRF) block list now also covers NAT64, 6to4, Teredo and reserved IPv4 ranges.
- Concurrent upstream fetches are bounded (16 at a time per server), and the upstream documents the proxy and group parse in memory (pypi, helm, nuget, cargo, OCI tag lists) share one concurrency gate.
- Maven, deb and rpm files without a published digest are no longer cached "forever" everywhere: `archetype-catalog.xml`, `.deb`/`.udeb` outside a `pool/` directory and `.rpm` outside a `Packages/` directory use `cache_ttl_seconds`, and an HTML `200` answer for a package path is refused with `502`. Already cached files keep their old expiry until evicted.

#### Organizations become projects

**Requires a Recreate upgrade.** Stop all old replicas before starting the new version; do not use a rolling upgrade. The migration renames tables the old binaries still query, so old and new replicas cannot run side by side.

### 0.5.0

> **Before upgrading a multi-replica deployment:** stop every pre-0.5.0 replica before the new version starts (Kubernetes: `strategy: Recreate`, or scale to 0 first). Migrations `018`, `019` and `022` change unique indexes and tables that older binaries write to, so old and new replicas cannot run side by side. The runtime image no longer contains a shell: with Helm chart 0.1.4 or older set `database.waitForDatabase=false` (the server waits for the database itself), or upgrade to chart 0.2.0.

> **Security: Go module repositories on 0.4.1 and earlier leak zips across repositories and projects.** Up to 0.4.1 the Go module upload stored every zip's database row without a digest, so all Go module versions of an instance shared one blob record that points at the **first** zip ever uploaded. Every `.zip` download in every Go repository, of any project, returned that one zip: a user who could read any Go repository could read the source of the first module published anywhere on the instance. **Upgrade, then check your Go repositories.**
>
> - Affected: every Go repository whose versions were uploaded on **0.4.1 or earlier**. Versions uploaded after the upgrade are not affected.
> - **Fail closed:** the new version answers `404` for any Go module zip whose blob has no valid sha256 and logs `refusing to serve go module zip ... re-upload the version or run the gomod repair` (repository, module, version). Nothing is served from the shared record any more, even if the repair below cannot fix a row.
> - **Automatic repair:** at every start a background task, run by one replica at a time (PostgreSQL advisory lock), looks for Go versions (trashed ones included) that still point at such a record. If there are none it exits at once. Otherwise it recovers each real zip from the blob store (the zips of later uploads were stored under their true sha256 and never deleted), checks it (content matches its sha256, every entry under one `<module>@<version>/` prefix, its `go.mod` equals the stored one) and relinks the version to it. The shared record is then deleted from the database; its object is never deleted, because it is a real module's zip. A version that matches several different stored zips (for example two forks publishing the same module path and version) is **not** guessed: it stays unservable.
> - **Re-run on demand:** `openartifact-server -repair-gomod` runs one repair pass and exits (same configuration and environment as the server; `0` when everything was repaired, non-zero when versions remain). It prints a summary and lists every unrepairable `repository: module@version`; the same lines are logged as warnings at startup.
> - **Re-upload what could not be repaired.** Those versions keep answering `404`; delete them and `PUT` the zip again ([Go modules](../formats/go.md#publish)). On storage backends that cannot list objects (`oci`) only the zip of the shared record itself can be recovered, so all other affected versions must be re-uploaded.
> - **Backups taken on 0.4.1 or earlier:** their Go module records carry no zip digest, so restoring skips those versions (logged, and the restore reports as incomplete); re-upload them. Migration `021` adds a database check (`blobs_sha256_hex`) so a blob record without a 64-hex sha256 can no longer be written; it does not scan existing rows, so the repair can still replace them.
> - Treat the first module's source as having been disclosed to every user who could read any Go repository on the instance, and rotate anything sensitive in it.

Migration `016` runs automatically at first start (adds `repositories.presign_downloads` and the `presigned_uploads` table). Default behavior is unchanged: downloads still stream through the server until you opt in to presigned URLs ([storage](../operations/storage.md#presigned-urls)).

## Rollback

Because migrations are forward-only, going back to an older version after a migration has run means restoring the database backup taken before the upgrade, then starting the older version. An older binary does not refuse a database with newer migrations (it only checks the migrations it knows), but a newer schema is not guaranteed to work with it. Restore the blob store snapshot that matches the database backup if artifacts were uploaded or deleted in between.
